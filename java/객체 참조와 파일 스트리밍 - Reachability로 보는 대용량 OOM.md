# 객체 참조와 파일 스트리밍 — Reachability로 보는 대용량 OOM

> 날짜: 2026-08-19

대용량 파일을 처리할 때, 왜 전체 적재 방식은 Heap을 크게 점유하고 스트리밍 방식은 이를 줄이는지 객체 참조 그래프 관점에서 정리한다.

## 내용

### JVM 구조 — 스택 프레임과 Heap의 역할 분리

메서드가 실행되면 해당 스레드의 Stack에 **스택 프레임(Stack Frame)** 이 만들어진다. `data`, `rows`, `records` 같은 지역 변수의 참조값은 이 스택 프레임에 있고, 실제 `byte[]`, `List`, 행 래퍼, 행 데이터 객체는 **Heap**에 있다.

인스턴스 필드는 Stack에 따로 저장되지 않는다. 예를 들어 행 래퍼 객체 자체와 그 안의 `record` 필드는 Heap에 있고, 실행 중인 메서드의 지역 변수 `rows`가 Stack에서 `List` 객체를 가리킨다.

```text
Stack Frame (process)
  rows ───────→ List<RowWrapper>             (Heap)
                    └→ RowWrapper           (Heap)
                         └→ record ───────→ Record (Heap)
```

`int length`처럼 원시값 필드는 다른 Heap 객체를 가리키지 않는다. 반면 참조형 필드인 `record`는 다른 객체로 이어지는 연결을 만든다.

> **면접 예상 질문:** 지역 변수, 객체, 객체의 인스턴스 필드는 Stack과 Heap 중 어디에 위치하는지 스택 프레임과 객체 참조를 연결해 설명해주세요.

---

### GC Root와 도달 가능성 — Reachable 객체는 회수되지 않는다

GC는 **GC Root**에서 시작해 참조를 따라갈 수 있는 객체를 찾는다. 실행 중인 스레드의 스택 프레임에 있는 지역 변수는 대표적인 GC Root이며, 여기에서 닿는 객체는 **Reachable(도달 가능)** 상태다. Reachable 객체는 쓰레기가 아니므로 GC가 회수하지 않는다.

반대로 GC Root에서 어떤 경로로도 닿지 않는 객체는 **Unreachable(도달 불가능)** 상태가 되어 회수 후보가 된다. 단, “메서드가 아직 끝나지 않았다”는 사실만으로 모든 지역 변수가 반드시 살아 있는 것은 아니다. 마지막 사용 이후의 실제 생존 여부는 JIT 최적화와 GC 시점에 따라 달라질 수 있으므로, 메서드 범위만 보고 모든 객체가 끝까지 유지된다고 단정하면 안 된다.

`rows.stream().map(RowWrapper::getRecord).collect(...)` 같은 변환은 `rows`의 래퍼에서 꺼낸 **같은 Record 참조**를 새 목록에 담는다. 즉 Record 객체를 복제하지는 않지만, 변환 중에는 다음이 함께 존재할 수 있다.

```text
rows     → List 내부 참조 배열 → RowWrapper → record ┐
                                                      ├→ 같은 Record
records  → List 내부 참조 배열 ────────────────────────┘
```

따라서 `rows`가 더 이상 도달 가능하지 않아지면 행 래퍼와 `rows`의 내부 배열은 회수 후보가 될 수 있다. 그러나 `records`가 같은 Record를 참조하는 동안에는 Record 객체는 계속 Reachable 상태다.

> **면접 예상 질문:** 두 List가 같은 데이터 객체를 참조할 때, 한 List가 사라져도 데이터 객체가 바로 GC되지 않는 이유와 추가로 발생하는 메모리 사용을 설명해주세요.

### File.readAllBytes() vs InputStream — 전체 버퍼링과 증분 처리

`Files.readAllBytes(file)`은 파일 전체 내용을 하나의 큰 `byte[]`로 만든다. 이후 파싱 결과를 전체 `List`에 모으고 결과물까지 메모리에 구성하면, 입력 크기에 비례하는 여러 객체가 Heap에 누적될 수 있다.

`InputStream`은 행이라는 단위를 아는 API가 아니라 **바이트를 순서대로 제공하는 스트림**이다. 행 단위 처리는 파서가 스트림에서 현재 레코드에 필요한 바이트만 읽고 하나의 Body를 만든 뒤, 즉시 다음 처리 단계로 넘길 때 만들어진다.

```text
readAllBytes 경로
파일 전체 → byte[] 전체 → List 전체 → Workbook 전체

InputStream 경로
파일 → 현재 행 바이트 → 현재 데이터 객체 → 현재 결과 단위 → 다음 행
```

스트리밍의 핵심은 `InputStream`이라는 타입 이름이 아니라, 파일 전체 `byte[]`와 전체 행 `List`를 만들지 않고 중간 결과의 수명을 짧게 만드는 처리 구조다.

> **면접 예상 질문:** `Files.readAllBytes()`와 `InputStream` 기반 파싱의 차이를 Heap 점유와 객체 생존 기간 관점에서 설명해주세요.

### 스트리밍의 공간 복잡도 — 행 수가 아니라 윈도우를 제한한다

전체 파일과 전체 행 목록을 유지하면 메모리 사용은 행 수에 따라 증가하므로 공간 복잡도는 O(n)이다. 반면 한 행을 변환해 기록하고, 결과 생성 라이브러리가 유지할 버퍼도 고정된 윈도우로 제한하면 동시에 살아 있는 행 객체 수는 전체 행 수와 독립적이다.

이때 전체 행 수를 기준으로 한 공간 복잡도는 O(1)에 가깝다. 엄밀히는 현재 행의 크기, 열 메타데이터, 라이브러리 버퍼, 출력 관련 상태는 남으므로 “메모리를 전혀 쓰지 않는다”는 뜻은 아니다. 핵심은 파일이 커져도 **전 행을 Heap에 누적하지 않는다**는 점이다.

`OutputStream`에 직접 기록하면 최종 결과 전체를 별도 `byte[]`로 만들 필요도 줄일 수 있다. 대신 이미 전송을 시작한 뒤 오류가 나면 수신자는 일부만 받은 결과를 갖게 되므로, 사전 검증과 타임아웃 정책이 필요하다.

> **면접 예상 질문:** 행 단위 스트리밍을 사용했을 때 공간 복잡도가 O(n)에서 O(1)에 가까워지는 이유와, 응답 스트리밍의 운영상 트레이드오프를 설명해주세요.

## 학습 정리

- Stack Frame의 지역 변수는 Heap 객체를 가리키는 참조값을 보관하며, 인스턴스 필드는 객체와 함께 Heap에 있다.
- GC Root에서 닿는 Reachable 객체는 GC가 회수하지 못하고, Unreachable 객체만 회수 후보가 된다.
- 두 List는 같은 데이터 객체를 공유할 수 있지만, 각 List의 내부 배열과 행 래퍼는 별도로 Heap을 사용한다.
- `Files.readAllBytes()`는 파일 전체 `byte[]`를 만들고, `InputStream` 기반 파싱은 파서가 필요한 바이트를 증분 소비한다.
- 스트리밍은 전체 입력이 아닌 현재 행과 고정된 버퍼만 유지해, 전체 행 수 관점에서 공간 복잡도를 O(1)에 가깝게 만든다.
