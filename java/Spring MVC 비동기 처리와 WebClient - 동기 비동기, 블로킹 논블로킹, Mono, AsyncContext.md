# Spring MVC 비동기 처리와 WebClient — 동기·비동기, 블로킹·논블로킹, Mono, AsyncContext

> 날짜: 2026-08-18

## 내용

### 동기·비동기와 블로킹·논블로킹 — 서로 다른 기준

두 쌍은 같은 뜻이 아니다. 혼동을 피하려면 먼저 **어느 주체의 관점인지**를 정하고, 질문을 분리한다.

| 구분 | 판단 기준 | 핵심 질문 |
|---|---|---|
| 동기 / 비동기 | 호출 결과를 이어서 처리하는 방식 | 결과가 준비될 때까지 호출 흐름이 기다려야 하는가? |
| 블로킹 / 논블로킹 | 호출 스레드의 점유 여부 | I/O 완료를 기다리는 동안 그 스레드가 다른 일을 할 수 있는가? |

- 동기 호출도 네트워크 응답처럼 시간이 오래 걸릴 수 있다. “동기 = 즉시 결과”가 아니다.
- 블로킹은 I/O가 끝날 때까지 **호출 스레드가 요청에 묶여** 다른 요청을 처리하지 못하는 상태다.
- 논블로킹은 I/O 완료를 기다리는 동안 호출 스레드를 계속 점유하지 않는 방식이다.
- 따라서 “비동기인데 나중에 결과를 기다리며 스레드를 묶는” 조합도 가능하다. 두 축을 항상 분리해서 설명한다.

파일 읽기 비유로 보면, 파일 읽기를 요청한 뒤 결과를 나중에 전달받는 것은 비동기 관점의 이야기이고, 그동안 담당자가 파일 앞에서 꼼짝 못 하는지는 블로킹 관점의 이야기다.

> **면접 예상 질문:** 동기/비동기와 블로킹/논블로킹의 판단 기준을 각각 설명하고, 두 개념을 같은 말로 보면 안 되는 이유를 말해주세요.

### I/O 대기와 스레드 점유 — CPU가 한가해도 발생하는 병목

I/O(Input/Output)는 디스크 파일, 데이터베이스, 네트워크 소켓처럼 프로그램 밖의 자원과 데이터를 주고받는 작업이다. 외부 HTTP API의 응답을 기다리는 것도 네트워크 I/O 대기다.

블로킹 I/O에서는 응답을 기다리는 스레드가 CPU를 계속 계산하는 것은 아니다. 운영체제는 그 스레드에 CPU를 주지 않고 다른 스레드를 실행할 수 있다. 하지만 서버의 스레드 풀 관점에서는 그 스레드가 해당 요청에 배정된 상태로 남으므로, 다른 HTTP 요청에 재사용할 수 없다.

즉 **CPU 사용률이 낮아도 스레드 풀이 고갈될 수 있다.** 스레드 풀에 200개가 있고 각 요청이 500ms 동안 외부 I/O를 블로킹으로 기다리면, 이상적인 처리량 상한은 대략 `200 / 0.5초 = 400 RPS`가 된다. 이는 CPU 연산 한계가 아니라 동시 대기 가능한 스레드 수의 한계다.

> **면접 예상 질문:** CPU 사용률은 낮은데 톰캣 워커 스레드가 모두 사용 중이라면, 어떤 종류의 병목을 의심해야 하며 왜 그런 상황이 가능한가요?

### Mono와 WebClient — 결과값 대신 완료될 작업을 반환하기

`Mono<T>`는 미래에 `T` 값 0개 또는 1개를 전달하거나 완료·오류 신호를 내보내는 Reactor의 Publisher다. `Mono`라는 타입 자체가 항상 별도 스레드나 비동기 실행을 보장하는 것은 아니다. 실제로 논블로킹인지 여부는 그 안에 연결된 I/O 작업과 중간 연산이 무엇인지에 따라 판단한다.

WebClient로 외부 HTTP 요청을 만들고 결과를 `Mono`로 반환하면, 컨트롤러는 외부 응답값을 즉시 얻으려고 대기하지 않고 “나중에 완료될 작업”을 Spring MVC에 넘길 수 있다. 네트워크 응답이 준비되면 Reactor Netty 이벤트 루프가 소켓의 준비 상태를 감지하고, 이후 `Mono` 파이프라인이 값 또는 오류 신호를 전달한다.

주의할 점은 논블로킹 HTTP 호출 중간이나 뒤에 JDBC·파일 접근처럼 블로킹 작업을 이벤트 루프에서 실행하면 이벤트 루프가 멈출 수 있다는 것이다. 이 경우 블로킹 작업은 별도 스케줄러로 분리할 수 있지만, 스레드 전환 비용과 별도 풀의 크기·대기열을 함께 관리해야 한다.

> **면접 예상 질문:** `Mono`를 반환한다고 해서 항상 논블로킹이라고 말할 수 없는 이유와, WebClient의 외부 HTTP 응답이 도착한 뒤 Reactor Netty가 수행하는 역할을 설명해주세요.

### Spring MVC 비동기 서블릿 — 워커 반납과 HTTP 연결은 별개

전통적인 동기 서블릿 처리에서는 톰캣 워커 하나가 컨트롤러 진입부터 최종 HTTP 응답 작성까지 요청을 맡는다. 컨트롤러가 `Mono`처럼 비동기 반환 타입을 반환하면 Spring MVC는 서블릿 비동기 처리로 전환할 수 있다.

이때 톰캣 워커가 풀로 돌아간다고 해서 클라이언트 HTTP 연결이 곧바로 닫히는 것은 아니다. 서블릿 컨테이너는 `AsyncContext`를 통해 아직 완료되지 않은 요청·응답의 상태를 보존한다. 외부 I/O가 끝나 `Mono`가 완료되면 Spring MVC는 보류해 둔 최초 요청의 최종 HTTP 응답(JSON 등)을 작성하고 비동기 처리를 완료한다.

따라서 다음 두 문장을 구분해야 한다.

- **클라이언트 연결:** 최종 HTTP 응답을 받기 전까지 열린 채로 기다릴 수 있다.
- **톰캣 워커 스레드:** 외부 I/O를 기다리는 시간에는 요청에서 분리되어 다른 요청을 처리할 수 있다.

클라이언트 쪽 코드가 동기인지 비동기인지는 서버의 구현만으로 판단할 수 없다. 호출하는 코드가 응답을 받은 뒤에야 다음 일을 하는지, 또는 콜백·Promise·Future처럼 완료 신호를 받아 이어서 처리하는지를 별도로 확인해야 한다.

> **면접 예상 질문:** Spring MVC 컨트롤러가 `Mono`를 반환할 때, 외부 HTTP 응답 대기 중 톰캣 워커 스레드·클라이언트 연결·`AsyncContext`는 각각 어떤 상태인지 설명해주세요.

## 학습 정리

- 동기/비동기는 결과를 이어서 처리하는 방식, 블로킹/논블로킹은 호출 스레드가 I/O 대기에 점유되는지의 문제다.
- 외부 HTTP 응답을 기다리는 것은 네트워크 I/O 대기이며, 블로킹 I/O는 CPU가 낮아도 서버 워커 풀을 고갈시킬 수 있다.
- `Mono`는 결과값이 아닌 완료될 작업을 표현하는 Publisher이며, 그 자체만으로 논블로킹을 보장하지는 않는다.
- Spring MVC의 비동기 서블릿 처리는 워커 스레드를 반납해도 클라이언트 연결과 요청 상태를 유지할 수 있게 한다.
- 서버 워커의 논블로킹 여부와 클라이언트 코드의 동기/비동기 여부는 서로 다른 주체·다른 판단 대상이다.
